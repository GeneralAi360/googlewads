## Canonical user-facing production path

The intended UX is now:

`QUESTIONS / INTAKE`
`→ EXACT COMMERCIAL JOB LOCK`
`→ RESEARCH / STRATEGY`
`→ FIRST-ROUND VISUAL EXPLORATION`
`→ USER SELECTS A DIRECTION`
`→ REVISE / APPROVE SELECTED VISUAL`
`→ PRODUCTION ASSET COMPLETION IF NEEDED`
`→ PRODUCTION REPRESENTATIVE / FIDELITY`
`→ CAMPAIGN DESIGN SYSTEM`
`→ FULL PRODUCTION`
`→ GOOGLE TECHNICAL + POLICY PREFLIGHT`
`→ REVIEW / DELIVERY`

If the user explicitly locked a visual direction beforehand, the first-round exploration may use a single concept. An internal recommendation, Style Intelligence recommendation, category recommendation, prior Work recommendation, or reviewer preference is **not** a user lock.

## Commercial-job gate — REAL-06

Product identity, campaign objective, CTA, and the exact commercial transaction/service job are separate facts.

For Bitrix24, these are materially different jobs:

- `NEW_LICENSE_PURCHASE`;
- `LICENSE_RENEWAL`;
- `PURCHASE_OR_RENEWAL`;
- `IMPLEMENTATION_SERVICE`;
- `CONSULTATION`.

New canonical artifacts:

- `references/commercial-job-and-concept-exploration.md`;
- `schemas/campaign-commercial-job.schema.json`;
- `scripts/validate_campaign_commercial_job.py`.

A material commercial-job change returns `COMMERCIAL_JOB_CHANGED` and invalidates meaning-dependent downstream artifacts rather than preserving the old design with a copy edit.

For `PURCHASE_OR_RENEWAL`, the controller must resolve whether purchase/renewal are deliberately `COMBINED` or represented as `SEPARATE_VARIANTS`.

## Visual exploration gate — REAL-06

`deliverables.concept_count` means the number of final creative concepts to be produced/scaled. It does **not** mean the number of alternatives the user sees before choosing the visual system.

A campaign may therefore have:

- final `concept_count = 1`;
- first-round `visual_exploration_count = 3`.

Unless explicit `USER_LOCKED` evidence exists, the first visual round must use:

`EXPLORE_3`

and show exactly three materially different rendered concepts in the same representative size.

New canonical artifacts:

- `schemas/visual-concept-set.schema.json`;
- `scripts/validate_visual_concept_set.py`.

Every pair of first-round concepts must differ on at least three of these axes:

1. hero logic;
2. composition system;
3. attention profile;
4. typography profile;
5. graphic device;
6. lighting language.

Palette swaps, crop changes, different button colors, or three versions of the same copy-left/image-right SaaS layout do not satisfy exploration.

Before a concept is shown to the user, an exact rendered-artifact `ART_DIRECTOR_REVIEWER` must PASS:

- commercial-job fidelity;
- professional category fit;
- `ad_not_presentation_slide`;
- hierarchy;
- typography;
- CTA integration;
- visual distinctiveness;
- anti-template quality;
- small-format viability.

A failed concept must be revised internally before presentation. The user is not the first basic QA pass.

For `EXPLORE_3`, user-facing presentation should contain:

- one comparison/contact sheet with A/B/C;
- each individual rendered concept;
- one short concept card per direction;
- a simple selection request: `SELECT A`, `SELECT B`, `SELECT C`, `REVISE`, or `REJECT ALL`.

## Production asset readiness versus visual concept visibility — REAL-03 / REAL-05

Production asset readiness and user concept visibility are separate concerns.

Production `NEEDS_ASSET` blocks:

- treating concept-only surrogates as production assets;
- production representative when required real assets are missing;
- scale-out / full pack;
- final exact-artifact technical/policy clearance;
- delivery-ready claims.

It does **not** by itself block:

- IDEA_ARCHITECTURE;
- VISUAL_CHARACTER;
- Style Intelligence;
- attention / typography;
- LIGHTING_INTENT;
- internal art direction;
- pre-render Google policy risk;
- a safe user-facing concept preview.

Safe preview modes remain:

- `PRODUCTION_ASSET`;
- `REFERENCE_ONLY_SURROGATE`;
- `LOW_RES_AUTHENTIC_SURROGATE`;
- `STRUCTURAL_PLACEHOLDER`;
- `TEXT_BRAND_PLACEHOLDER`.

Fake/generated product UI and fake/generated logos remain prohibited even in a preview.

A surrogate preview stays:

- `approval_scope = VISUAL_SYSTEM_WITH_ASSET_SLOTS`;
- `production_asset_readiness = NEEDS_ASSET`;
- `not_for_delivery = true`.

## Visual approval boundary — REAL-04 / REAL-05

The user approves what they can actually see.

Written art direction is an internal production contract and cannot substitute for visual approval.

After the user selects one first-round concept:

- `APPROVE` binds the exact visible artifact/system;
- `REVISE` requires a new rendered version and another visual decision;
- `REJECT` returns to the smallest responsible upstream layer;
- if all first-round concepts are rejected, create a new materially different exploration set rather than cosmetic remixes.

Two approval scopes remain:

### `EXACT_PRODUCTION_ARTIFACT`

All production assets are ready; user approves the exact representative bytes.

### `VISUAL_SYSTEM_WITH_ASSET_SLOTS`

Production assets are still missing; user approves the visible design system, not temporary asset bytes. Status becomes `VISUAL_CONCEPT_APPROVED_ASSET_PENDING`; full production stays blocked until real assets are supplied and fidelity is verified.

After real asset substitution:

- fidelity `PASS` may continue without redundant second user approval;
- `MATERIAL_DRIFT` requires showing the changed production representative again.

A reviewer may attest fidelity but cannot manufacture user approval.

## Google Ads policy acceptance gate

Before a real pack is called `Google-ready`:

- current English Google Advertising Policies are checked or the local snapshot is fresh;
- every final banner has an exact-SHA policy review;
- misleading system/dialog/pseudo-control/download-install/pseudo-interaction/segmented/transparent-background issues are absent;
- image/text quality is policy-acceptable;
- material claims and qualifiers are verified;
- real landing page supports the actual offer and CTA;
- destination working/domain/crawlability/geo/accessibility evidence is resolved;
- advertiser identity and affiliation claims are verified;
- trademark use is contextually resolved;
- restricted-vertical/certification/targeting states are resolved when applicable;
- pack aggregation is `GOOGLE_POLICY_PREFLIGHT_PASS`;
- final local status is `GOOGLE_READY_PRECHECK_PASS`.

Local policy preflight never guarantees actual Google approval.
