# v0.2 Release Gate

`dev/performance-banner-designer-v0.2` is an active release-candidate hardening branch, not a completed release.

## Real Work regression classes

Real acceptance has now produced eight permanent regression classes:

- `REAL-01` — premature rendering before enough category/competitor research; superficially different directions; generic/toy-like B2B imagery; insufficient professional category fit.
- `REAL-02` — stronger research-first direction still drifted into an unapproved CTA / ambiguous brand identity and correctly exposed the need for real product UI/logo assets.
- `REAL-03` — a correct production `NEEDS_ASSET` state was applied too early and incorrectly skipped IDEA / VISUAL_CHARACTER / Style Intelligence / attention / typography / LIGHTING_INTENT.
- `REAL-04` — the user clarified that the approval artifact must be the rendered visual concept itself, not a text-only art-direction description.
- `REAL-05` — production asset blockers still caused the system to show no actual visual concept to the user even after strategy had completed.
- `REAL-06` — the system designed the wrong commercial job (`IMPLEMENTATION_SERVICE` instead of Bitrix24 license purchase), treated an internal A2 recommendation as if it were a user lock, showed only one concept, and allowed a weak presentation-slide-like visual to reach the user.
- `REAL-07` — Work reported `PRESENTATION_READY_DESIGN` while still in image generation and surfaced generic abstract blue/metal hero imagery rather than complete banner composites. This exposed raw-asset/banner-role confusion and a pre-show review false positive.
- `REAL-08` — even after complete-banner and review hardening, the system repeatedly invented pseudo-premium blue glass/metal geometry because it began visual exploration before the **advertising/design problem itself** had been approved. The missing control was a user-approved Graphic Banner Brief before any A/B/C rendering.

## Canonical user-facing production path

The intended UX is now:

`QUESTIONS / INTAKE`
`→ EXACT COMMERCIAL JOB LOCK`
`→ RESEARCH / CATEGORY EVIDENCE`
`→ GRAPHIC BANNER BRIEF`
`→ USER: APPROVE BRIEF / REVISE BRIEF`
`→ IDEA / PRESENTATION / EMOTION / VISUAL CHARACTER`
`→ STYLE INTELLIGENCE / ATTENTION / TYPOGRAPHY / LIGHTING`
`→ INTERNAL ART DIRECTION`
`→ FIRST-ROUND VISUAL EXPLORATION`
`→ OPTIONAL COMPONENT-ASSET GENERATION`
`→ COMPLETE BANNER COMPOSITES`
`→ TWO FRESH EXACT-ARTIFACT PRE-SHOW REVIEWS`
`→ USER SELECTS / REVISES / APPROVES VISUAL`
`→ PRODUCTION ASSETS / FIDELITY`
`→ CAMPAIGN DESIGN SYSTEM`
`→ FULL PRODUCTION`
`→ GOOGLE TECHNICAL + POLICY PREFLIGHT`
`→ REVIEW / DELIVERY`.

There are now **two distinct user gates** before scale-out:

1. `APPROVE BRIEF` — approves the advertising/design problem and constraints.
2. `APPROVE` on a rendered visual — approves the visible design system.

Neither substitutes for the other.

## Commercial-job gate — REAL-06

Product identity, campaign objective, CTA, and exact commercial transaction/service job remain separate facts.

Current normalized jobs include:

- `NEW_LICENSE_PURCHASE`;
- `LICENSE_RENEWAL`;
- `PURCHASE_OR_RENEWAL`;
- `IMPLEMENTATION_SERVICE`;
- `CONSULTATION`.

Canonical artifacts:

- `references/commercial-job-and-concept-exploration.md`;
- `schemas/campaign-commercial-job.schema.json`;
- `scripts/validate_campaign_commercial_job.py`.

A material commercial-job change returns `COMMERCIAL_JOB_CHANGED` and invalidates meaning-dependent downstream artifacts rather than preserving the old design with a copy edit.

That invalidation now explicitly includes any stale Graphic Banner Brief and its user decision.

## Graphic Banner Brief gate — REAL-08

After exact commercial-job resolution and relevant research/category evidence, the skill must create a user-reviewable Graphic Banner Brief **before** visual exploration.

Canonical artifacts:

- `references/graphic-banner-brief.md`;
- `schemas/graphic-banner-brief.schema.json`;
- `scripts/validate_graphic_banner_brief.py`;
- `schemas/graphic-banner-brief-decision.schema.json`;
- `scripts/validate_graphic_banner_brief_decision.py`;
- `evals/real-world-failure-real08.json`.

The brief freezes at least:

- commercial core / product / exact job / CTA / brand;
- audience decision context;
- first-glance takeaway;
- primary / secondary / forbidden message semantics;
- desired user reaction;
- banner role / persuasion / trust mechanism;
- visual-semantic job;
- composition hierarchy, scan roles, CTA integration and brand anchor;
- typography constraints;
- color / lighting boundaries;
- desired / forbidden graphic character;
- anti-failure rules;
- concept-generation rules;
- presentation-ready quality bar.

A valid pre-decision brief returns:

`GRAPHIC_BANNER_BRIEF_READY_FOR_USER_APPROVAL`

with:

- `render_allowed=false`;
- `full_production_allowed=false`.

The user sees a concise human-readable brief and chooses only:

- `APPROVE BRIEF`;
- `REVISE BRIEF`.

Only exact current brief bytes plus:

- `decided_by = USER`;
- `decision = APPROVE`;

may produce:

`GRAPHIC_BANNER_BRIEF_APPROVED`

and:

`visual_exploration_allowed=true`.

`REVISE` requires feedback and keeps all visual rendering blocked until revised brief bytes are approved.

No controller, Style Intelligence agent, art director or reviewer can approve this gate for the user.

### REAL-08 anti-failure floor

The approved brief must hard reject at least:

- abstract geometry without commercial meaning;
- decorative form substituted for advertising idea;
- raw generated image used as concept;
- presentation-slide composition;
- generic 3D object without task-specific meaning;
- missing brand anchor;
- commercial job not understandable at first glance;
- a visual that needs a long rationale to acquire meaning;
- visual novelty replacing clarity.

Hero generation is optional and cannot be the default first step.

A/B/C must differ by **advertising logic** before they differ by visual form. `light 3D / dark 3D / typography` is not a sufficient strategic exploration model.

## Visual exploration gate — REAL-06 / REAL-08

Final campaign concept count and first-round exploration count remain separate.

Unless explicit `USER_LOCKED` evidence exists, first visual round uses:

`EXPLORE_3`.

But `EXPLORE_3` is now blocked until `GRAPHIC_BANNER_BRIEF_APPROVED`.

Every concept shares the exact approved commercial/brief constraints while differing materially in advertising logic and visual grammar.

Every pair still differs on at least three design axes:

1. hero logic;
2. composition system;
3. attention profile;
4. typography profile;
5. graphic device;
6. lighting language.

## Raw hero asset != banner concept — REAL-07

`HERO_ASSET_CANDIDATE` remains an upstream component only.

The only valid user-facing concept artifact is:

`artifact_role = BANNER_COMPOSITE`.

Every concept preview binds complete visible message / commercial cue / CTA / brand anchor and actual representative raster bytes.

Generic/stalled image generation must be abandoned rather than becoming the workflow.

## Two fresh exact-artifact pre-show reviews — REAL-07

Every complete first-round concept still requires two fresh review contexts bound to the exact banner bytes, with distinct reviewer-context IDs and no prior-verdict visibility.

`PRESENTATION_READY_DESIGN` requires evidence-bearing PASS for commercial fidelity, composite completeness, message/CTA/brand presence, hero semantic relevance, advertising impact, composition, typography, polish, premium category bar, non-generic identity, ad-not-slide and small-format viability.

The user must not be the first basic visual QA pass.

## Asset truth / visual approval

Production `NEEDS_ASSET` remains fail-closed for final production but does not automatically hide a safe concept preview.

The user approves rendered visual design, not the Graphic Banner Brief, written art direction or raw generated component.

After user visual approval, production asset substitution still requires fidelity; material drift requires reapproval.

## Google Ads policy acceptance gate

Before a real pack is called locally Google-ready, exact-artifact technical and policy evidence must pass for every final banner, including misleading design, image/text quality, claims/qualifiers, destination support, advertiser identity, affiliation/trademark context and applicable restricted-vertical/targeting requirements.

Local policy preflight never guarantees actual Google approval.

## Merge rule

Do not merge because CI is green.

Merge only after real Work acceptance of the Graphic Banner Brief → visual exploration → user visual approval flow, real-pack policy acceptance, independent rigor (or explicit degraded-rigor acceptance), and explicit user approval.

Until then:

- deterministic engineering: `ACTIVE_HARDENING`;
