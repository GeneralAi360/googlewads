# v0.2 Release Gate

`dev/performance-banner-designer-v0.2` is an active release-candidate hardening branch, not a completed release.

Real Work acceptance has produced two permanent regression classes:

- `REAL-01` — premature rendering without category/competitor research, superficially different art directions, generic/toy-like B2B imagery and insufficient professional category fit;
- `REAL-02` — a much stronger research-first direction that still drifted into unapproved CTA wording and ambiguous brand identity while correctly requiring real product UI.

The user-supplied visual-methodology presentation added another deterministic requirement: the pipeline must freeze **idea → presentation → emotion → visual character → lighting intent** before art direction and must freeze a campaign design system before scale-out.

## Upcoming style-example integration gate

The user's next banner-style examples are an intentional part of v0.2 hardening.

They must be:
- analyzed as references / style evidence;
- mapped into `VISUAL_CHARACTER`, `style_tags`, composition/typography/image/lighting DNA;
- compared against current character axes and expanded if the axes are insufficient;
- kept as an extensible vocabulary rather than a compulsory finite style list;
- connected to `LIGHTING_INTENT` so every style specifies whether light is structural, atmospheric, material-defining, graphic, neutral, or not applicable;
- added to eval/regression cases if they reveal systematic failures.

Do not encode any style as “high-converting” without performance evidence.

## Independent rigor gates

- [ ] six hidden-key visual eval cases executed by genuinely fresh visual reviewer contexts and scored;
- [ ] final repository/PR reviewed by a genuinely independent reviewer context;
- [ ] important independent findings reconciled and final-head CI re-run.

## Merge rule

Do not merge into `main` merely because deterministic CI is green.

Merge only when:
1. deterministic CI is green on the final head;
2. the real Work acceptance gates above pass;
3. the upcoming style-example integration has been evaluated;
4. independent rigor gates are satisfied, **or** the user explicitly accepts degraded rigor;
5. the user explicitly approves merge.

Until then:
- deterministic engineering: `ACTIVE_HARDENING`;
- real user-acceptance validation: `RETEST_REQUIRED`;
- delivery/runtime rigor: `NOT_FULLY_VALIDATED`;
- merge: `BLOCKED_BY_RELEASE_GATE`.
